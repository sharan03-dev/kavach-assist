# The course exercises behind Kavach (23CSE528 NoSQL Database using MongoDB)
## Exercises 1 to 6: the MongoDB foundations used by the chat application
Exercise 1 introduces NoSQL and the document model: data is stored as flexible JSON-like documents in collections instead of rows in tables. Exercise 2 sets up MongoDB (locally and on the Atlas cloud) and connects to it with a connection string kept in an environment variable. Exercise 3 covers CRUD: insertOne, find, updateOne, deleteOne. Exercise 4 covers queries with filters, projections, sorting and limits. Exercise 5 covers the aggregation pipeline ($match, $group, $sort, $lookup, $facet). Exercise 6 covers indexes (single, compound, text, TTL, unique) and explain(). Kavach Assist uses all of them: the threat board is one $facet aggregation, every chat query uses a compound index, sessions use upserts, and rate-limit windows expire through a TTL index.
## Exercise 7 (Lab 7): schema design and the Kavach platform
Lab 7 builds Kavach, the cyber threat intelligence website (FastAPI + MongoDB). It downloads real feeds (CISA KEV, GCVE sightings, blocklists, security news), classifies reports, and stores them in collections reports, indicators, sightings, vulnerabilities, threat_actors and sources. Lab 7.1 is schema design: embed data that is read together (the KEV entry is embedded 1:1 in a vulnerability) and reference data that grows without bound (sightings are a separate collection, 1:many). Lab 7.2 studies the WiredTiger cache with a 100,000-document working set and measures the cache hit ratio.
## Exercise 8 (Lab 8): replica set and high availability
Lab 8 runs three MongoDB servers (mongo1, mongo2, mongo3) as replica set rs0. One PRIMARY accepts writes, two SECONDARY members copy the oplog. If the primary fails, the others hold an election and one becomes primary in about 10 to 12 seconds, so the website keeps working. Read preference decides which member answers reads. Kavach Assist stores users and conversations on this replica set.
## Exercise 9 (Lab 9): write concern and network partitions
Lab 9 measures write concern. w:1 is acknowledged by the primary only: fast, but a write can be rolled back if the primary dies before replicating. w:majority waits for 2 of 3 members: slower, but the write survives a failover. j:true also waits for the journal. The partition activity disconnects a member and shows that a minority side cannot accept majority writes (CAP theorem: MongoDB chooses consistency over availability during a partition). Kavach Assist writes conversations with w:majority.
## Exercise 10 (Lab 10): multi-document ACID transactions
Lab 10 adds a billing paywall to the classifier: three free uses, then top up a wallet and subscribe. Money moves inside multi-document transactions with snapshot isolation, so debit, subscription and payment record commit together or not at all. Concurrency tests show no lost updates and no double spending; idempotency keys make retries safe.
## Exercise 11 (Lab 11): sharding
Lab 11 builds a sharded cluster: a config server replica set, two shards (shardA and shardB) and the mongos router. A good shard key has high cardinality, is not monotonically increasing and matches the queries; a hashed key spreads writes evenly, a ranged key keeps range queries on one shard. The lab shows a hotspot caused by a monotonic key, targeted versus scatter-gather queries, and resharding.
## Exercise 12 (Lab 12): security
Lab 12 hardens MongoDB: SCRAM-SHA-256 authentication, role-based access control with least privilege, TLS with client certificates (connections without a trusted certificate are refused), client-side field level encryption so UPI ids are ciphertext even for the database administrator, schema validation, auditing with the profiler and change streams, IP allow-lists and redacting views. Kavach Assist applies the same ideas: secrets only in environment variables, hashed passwords, roles, and an audit log.
## Exercise 13 (Lab 13): containers and cloud
Lab 13 runs a production-style replica set in Docker Compose with a keyfile, health checks and restart policies, proves that a kill -9 of the primary loses zero acknowledged writes, adds a Prometheus exporter sidecar, repeats the deployment as a Kubernetes StatefulSet, and reviews a Terraform file for MongoDB Atlas. Kavach Assist is deployed the same way: Docker Compose services with a /health endpoint for the container health check.
## Exercise 14 (Lab 14): operations, monitoring and backup
Lab 14 monitors the production set (replication lag, cache hit ratio, connections) every 30 seconds, sends webhook alerts in Slack and Discord format, takes mongodump backups with 7-day retention, verifies restores by checksum, and performs point-in-time recovery with the oplog to the second before an incident. Kavach Assist records latency, errors and LLM token usage for every chat request and exposes them at /metrics.
## Exercise 15 (Lab 15): the SaaS product TaskTracker
Lab 15 builds a multi-tenant REST API: every document carries tenant_id and every query filters on it, JWT tokens identify user and tenant, role-based access separates admins from members, an atomic counter enforces rate limits (HTTP 429), and a migration moves tenants between a shared collection and per-tenant collections without leaks. Kavach Assist reuses the JWT login, the roles and the atomic rate limiter on the /chat endpoint.
## Exercise 16 (Lab 16): Cassandra and Neo4j (polyglot persistence)
Lab 16 compares three models on the same data. MongoDB (document) is the general-purpose store; Cassandra (wide-column) is designed query-first for very fast writes and time-series reads by partition key; Neo4j (graph) answers relationship questions such as fraud rings (money moving A to B to C and back to A) with Cypher. Lab 16.2 builds a FraudQueryService with connection pooling and a circuit breaker that opens after 3 failures and retries after 30 seconds.
## Exercise 17 (Lab 17): vector search and RAG
Lab 17 turns text into embeddings (384 numbers from the all-MiniLM-L6-v2 model) and stores them next to the text. MongoDB Atlas Vector Search finds the nearest chunks by meaning with $vectorSearch. RAG = retrieve the best chunks, then let a language model answer using only them, citing sources. Conversation memory is stored in MongoDB so follow-up questions work. Lab 17.2 compares HNSW (graph index: fast, high recall, more memory) with IVF (cluster lists: smaller, recall depends on nprobe). Kavach Assist is this pipeline applied to live threat data.
## Exercise 18 (Lab 18): the capstone comparison
Lab 18 loads 100,000 threats into MongoDB, Cassandra and Neo4j and runs the same four queries ten times each. MongoDB wins general lookups and has the simplest code, Cassandra wins time-bucket analytics by partition key, and Neo4j is best for relationship questions such as co-reporting communities found with Louvain. The lab also detects false-positive indicators (about 0.90 precision) and recovers 8 of 8 planted campaigns. Recommendation: MongoDB as the main operational and AI database, Cassandra for very large write-heavy logs, Neo4j for graph analytics.
## How the labs depend on each other
The labs form a chain: starting Lab N first starts Lab 7, then 8, and so on up to N, as Docker Compose dependencies with health checks. Only one lab runs at a time because Lab 13 deliberately crashes database members. Reports for every lab are written to the results folder as PDF.
